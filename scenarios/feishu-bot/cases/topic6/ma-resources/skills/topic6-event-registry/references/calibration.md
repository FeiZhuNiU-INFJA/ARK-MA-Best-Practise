# 置信度校准与质量验收

## 为什么必须先校准

模型输出的 `confidence` 是自我报告，不是校准过的概率。**未校准的置信度是没有刻度的仪表。**

硬证据：某次实跑中廉价模型给出 1112 条 `NON_EVENT + high confidence`，用强模型逐条复核，**547 条（49%）是错的**。误删集中在具名营销活动、具名作品、事件解读三类。

如果当时按 `confidence > 0.8 直接采信` 路由，这 547 条会静默流失，而且在产物里查不到痕迹。

**所以第一版：`confidence` 只落盘，不参与任何路由。** 校准跑完之前不要写任何自动路由阈值。

## 抽样单位是事件，不是记录

要测的是「合并对不对」，而**合并只发生在多成员事件里**。按记录随机抽会全落在单成员上——那一类根本没有合并判断，抽再多也测不出误并。

| 表 | 抽样量 | 测什么 |
|---|---|---|
| 多成员事件 | **默认全查** | False Merge Rate、该拆未拆、名称不覆盖成员 |
| 单成员记录 | 80 条，附上同块的多成员事件 | 漏并率 |
| 非事件记录 | 100 条，按 `reason_code` 分层 | 误杀率 |

多成员事件默认全查是因为它们数量本来就不多（382 条产出 49 个），而且它们是主要产出——每个都值得看。

单成员抽样必须**附上同块的多成员事件**，否则人工无从判断「它是否本该并进某个事件」。

非事件单独一张表，因为它是**唯一会真正丢数据**的判定——其他所有错误都还留在库里可以修。

## gt_verdict 取值

### 多成员事件

| 值 | 含义 |
|---|---|
| `CORRECT` | 成员都该在一起 |
| `WRONG_MERGE` | 混进了不该在的成员 —— **最重要** |
| `SHOULD_SPLIT` | 整个事件该拆成两个以上 |
| `WRONG_NAME` | 成员对但名字不覆盖成员 |
| `AMBIGUOUS` | 材料不足以判断 |

判 `WRONG_MERGE` 时在 `应移出的记录` 列写下该移出的标题片段——不写这一列，后面无法定位是判据问题还是少样本没覆盖。

### 单成员

`CORRECT`（确实独立）/ `SHOULD_MERGE`（漏并，在 `应并入` 写 event_id）

### 非事件

`CORRECT` / `WRONG`（误删）

## 人工判断依据

问「**这些热点背后能提供的创作灵感参考，是一个还是多个？**」
一个就该合、不同切入点进二级角度；多个就该拆。

- 票房破 2 亿到 8 亿 → 一个方向「影片大卖」，该合
- 游戏某版本的剧情 / 地图 / 卡池 / 新玩法 → 一个方向「版本上线」，该合
- 同一场典礼的红毯 / 获奖 / 票数 / 某明星话题 → 一个方向，该合
- 台风登陆致灾 vs 官方辟谣涉汛谣言 → 两个方向「灾情应对」「信息治理」，该拆
- 同一主体的多个事项（关店 / 房租 / 招聘） → 优先当一个方向；只能用空词命名才拆
- 不同届次 / 版本号 / 赛季 / 场次 → 该拆

不要用「能不能单独成为一条热搜」当判据——票房每次突破都能单独上榜，但灵感只有一个。

第三方指控 + 当事方回应属于判断项：争议体量足以独立支撑一个话题方向时独立成一级，
否则作为二级角度。

## 清洗环节单独验收，而且是全量

清洗（阶段 ⓿）和其他阶段不一样：它的产物是**确定性对照**（原标题 → clean_title），
可以逐条人工核对。这是整条流水线里唯一能全量验收的环节，别把它降级成抽样。

打开 `out/00_clean_titles.csv`，按三类看：

| 看什么 | 判什么 | 不合格的处置 |
|---|---|---|
| `reverted=True` 的行 | 本地校验拦下了什么（`NEW_NUMBER` / `NEW_CHAR` / `NEW_SEPARATOR` / `EMPTY`） | 比例应接近 0。偏高说明规则在教模型改写而不是删包装，改提示词重跑 |
| `ops=NONE` 但明显有包装的行 | 该删没删 | 补充该平台规则里的实例 |
| `ops` 非空的行 | 不该动却动了、或删掉了事实 | 同上 |

**最危险的一类是校验抓不到的：删掉了事实。** 本地校验只查「加」不查「删」——
新增数字和新增汉字能自动拦下，但把 `票房破8亿` 删成 `票房` 不会触发任何标志。
核对时重点确认日期、数字、比分、版本号、金额、届次、作品名一个都没少。

清洗错误的危害在于它**不可追溯**：下游拿到的就是清洗后的标题，
无论判定还是归档都不会察觉原文里还有别的信息。所以这一关必须人工过。

## 单平台聚合下的样本量问题

**每平台的多成员事件数会很少。** 4 平台混跑 382 条产出 49 个多成员事件；
拆成单平台后每个平台约 100 条，多成员事件可能只剩个位数到十几个。

后果与处置：

- 多成员事件**照旧全查**——数量少反而更容易全查，正确率仍然可算
- **置信度分档校准在单平台上做不了**。分档要求某一档 ≥20 条才允许自动路由，
  单平台凑不到。校准要合多个平台、多个窗口的样本一起算，
  但**前提是提示词与模型完全一致**（口径已统一到一套标准提示词，这个前提成立）
- False Merge Rate 在小样本上波动大，**单个平台单个窗口的数字不要当结论**，
  要累积多窗口再看趋势

## 指标定义

| 指标 | 定义 | 优先级 |
|---|---|---|
| **False Merge Rate** | 多成员事件里判 `WRONG_MERGE` 的比例 | **最高** |
| 多成员事件正确率 | 判 `CORRECT` 的比例 | 高 |
| 该拆未拆率 | 判 `SHOULD_SPLIT` 的比例 | 中 |
| 名称不覆盖成员率 | 判 `WRONG_NAME` 的比例 | 中 |
| 单成员漏并率 | 单成员里判 `SHOULD_MERGE` 的比例 | 中 |
| 非事件误杀率 | 非事件里判 `WRONG` 的比例 | **必须单独测** |

**False Merge Rate 必须最低。** 理由不对称：错拆还能在后续补救，错合会污染整个事件，并让事件名退化成「系列事件」这种没法用的形式。

漏并略高是可接受的代价——精度优先于召回。

## 校准表的产出与使用

按 confidence 分档统计多成员事件的实测错误率：

| confidence 区间 | 抽样量 | 实测错误率 | 建议处置 |
|---|---|---|---|
| ≥0.9 | | | |
| 0.8~0.9 | | | |
| 0.7~0.8 | | | |
| <0.7 | | | |

**只有在某一档抽样量 ≥20 且实测错误率足够低时，才允许对该档做自动路由。**

校准表写进 `run_manifest.json`，绑定 `prompt_version` + `model` + `input_hash`。换提示词或换模型，校准表作废必须重测——置信度分布会随两者变化。

**模型分层等校准结果，不能拍。** 哪个阶段能降级，只有实测错误率能回答。

## 验收指标

不用「最大簇不超过 N」这类工程指标——它靠调参就能达成，而调参恰恰是这套架构要消除的东西。

| 指标 | 目标 | 谁来查 |
|---|---|---|
| False Merge Rate | 优先压到最低 | 人工回填 `gt_verdict` 后由 `11` 算 |
| 多成员事件正确率 | 越高越好，这是主要产出的质量 | 人工抽检 |
| 非事件误杀率 | 单独测 | 人工抽检 `out/01_eventness.csv` |
| 空词事件名 | 0（本地拦截：先重命名，仍不合格才拆分） | 脚本 |
| 名称超 20 阅读单位 | 0 | 脚本，`x3` 出口打印剩余数 |
| 名称事实错误率 | 接近 0 | 脚本查数字与短词出处，长串靠人工 |
| 二级角度可用性 | 角度能直接支撑话题策划 | 人工 |
| 记录总数守恒（仅 Ⓧ 层） | 前后必须相等 | 脚本，不过就中止不写入 |
| 一条记录只属于一个事件（仅 Ⓧ 层） | 无例外 | 脚本，不过就中止不写入 |

「谁来查」这一列是为了别把脚本已经兜住的项再花人力核一遍——**脚本查的都是硬失败，
不会静默通过**，人工的注意力应该全放在语义项上（成员正确率、角度可用性、事实错误）。

## 两个隐藏问题，指标里看不出来

**事件定义过宽**：不体现在单条判定上，只在事件层面显现。检测方式是对成员数 ≥3 的事件，看名称是否需要并列连词或空词才能覆盖全部成员。这一项交 LLM 判，不要写正则——实测用阶段词白名单 + 字数阈值实现的机械规则，判对率只有 **28%**。

本流程已在阶段 07 用空词黑名单 + 重命名重试 + 兜底拆分处理了大部分，但语义层面的过宽仍需抽检。

**静默否决（漏召回）**：召回阶段没被圈进同一块的记录对，在后续任何阶段都不会被发现。所以 `candidates.jsonl` 的 `rejected` 必须落盘，校准时抽查一批 rejected 对，看是否有本该同事件的。这是唯一能发现召回层漏并的手段。

实测参考：cap60 分块下参考同事件对召回 **100%**（547 对一对没被切开），所以召回层目前不是瓶颈。但换数据集必须重测这个数——它是整套设计的前提。

**这 547 对的来源必须说清：它是上一版批次路线的输出，不是人工标注**（本目录三张校准表的
`gt_verdict` 至今 0 填）。所以它只能用来测「分块有没有切开已被合并的对」，
不能用来测合并对不对——那正是这三张表要人工填出来的东西。

单平台化之后同平台对只剩 375 对，微博 29、B站 23。**这个量级分辨不出个位数百分点的差异**，
任何基于它的 A/B 结论都要标注置信区间，不要直接拿来拍板。

## member_confidence 的双线阈值（x2）

两个 confidence 规则相反，不要混：

- **`model_confidence`（模型对自己判定的置信度）：只落盘，不做路由。** 不要写
  `>0.8 自动采信` 这类规则，直到跑完一轮 GT 校准。阶段 01 有过实测反例：廉价模型给出的
  1112 条「NON_EVENT + 高置信」里 547 条（49%）被强模型翻案。**未校准的置信度是没有
  刻度的仪表。**
- **`member_confidence`（成员归属置信度，07 产出）：可以路由，因为它有刻度。** 刻度写在
  07 的 SCHEMA 里，5 档，每档写明什么情况给什么分。

x2 按 `--cut 50 / --keep 75` 双线处理。**为什么是双线**：抽样 88 条人工判定后，
任何单一阈值都有明显误伤——

| 单一阈值 | 踢掉 | 误伤 |
|---|---|---|
| 50 | 15 | 0 |
| 60 | 28 | 9（32%） |
| 70 | 38 | 15（39%） |
| 75 | 48 | 23（48%） |

原因是分档质量**两头准、中间浑**：90 以上和 75~89 各抽 20 条全部正确，40 以下抽 8 条
全部正确，而 60~74 是 14 对 6、40~59 是 9 对 11。所以低于 50 自动剔除、50~74 交裁定、
75 以上直接保留，不取中间值一刀切。

**50 和 75 是在 88 条、单次合库数据上校准出来的，不是通用常数。** 样本上零误伤不等于
换一周仍零误伤。直接抄这两个数可以，但每次跑完要抽查 `out/x2_已剔除.csv` 的头几条,
看有没有明显该留的被踢掉。

**刻度不全时换模型没用。** 第一轮用 opus 裁定边界带改对 7 改错 8，看着是模型不行；但
它的错误全部落在当时刻度里没写的两类——「后续影响与派生数据」和「话题桶型事件的同题材
成员」。补进刻度后质量明显提升。**遇到判不准先查刻度缺不缺档，别先换模型。**
