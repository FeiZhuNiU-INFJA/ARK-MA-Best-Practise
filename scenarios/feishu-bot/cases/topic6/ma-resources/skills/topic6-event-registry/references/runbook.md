判定口径不在这里，在 [SKILL.md](../SKILL.md) 与 [identity.md](identity.md)。

## 异常速查表

**几乎所有异常都不需要从头重跑**，因为每个阶段都有断点。先在这张表里定位，
再决定动作——错误的第一反应（改参数、删目录、换 Key）往往比异常本身代价更大。

| 现象 | 真因 | 怎么办 |
|---|---|---|
| `SystemExit: 缺少凭据` | 环境变量没导出 | 见「授权」自检那条命令 |
| HTTP 401 / 403 | Key 失效或无该服务权限 | 换 Key。**不要先怀疑代码**，握手能过不代表 Key 有效 |
| **额度用尽 / quota exceeded** | 当前 Key 的配额跑光了 | **换备用 Key，然后原样重跑那一条命令**。已完成批次全部走缓存，不会重复计费也不会丢——实测中断在第 1280 条时，重跑缓存命中 70.5% |
| HTTP 429 | 限流 | 降 `--concurrency` 后重跑（这是唯一该降并发的场合）；不要改 `--batch-size`，它会打乱断点编号 |
| 工具超时 / 进程被杀 / 网络断 | 外部中断 | 原样重跑同一条命令，见「超时与中断」 |
| `socket connection closed` | 单次请求负载过大 | 减小 `--batch-size` 并**新建运行目录**重跑该阶段；在原目录改批量会让断点错位 |
| ⑦ 报「有 N 个块失败」 | 三类 JSON 失败之一 | 先原样重跑一次（②③ 会自动恢复）；仍失败再跑 `x1_presplit_blocks.py` + 重跑 ⑦ |
| ⑦ 报「覆盖不一致：期望 X 实得 Y」 | 有块没产出 | 与上一条同源，是失败块的连带现象，不是独立问题 |
| 阶段 00 报「校验不通过已回退原标题 N 条」 | 清洗时新增了汉字、数字或顿号 | **这是正常的保护动作**，不是故障。抽查一下被回退的行即可 |
| 向量化极慢（每秒个位数） | 用了要出海的 OpenAI 模型 | 确认 `--model` 是 `Doubao-embedding`，模型吞吐对比见 [benchmarks.md](benchmarks.md) |
| 成本台账数字明显偏低 | 失败轮次没记进台账 | 见「成本台账的已知缺陷」，按每块单价补估 |

**唯一需要删东西重来的情况**是「想换一套分块策略」——那时新建运行目录，
不要在原目录上改参数。


## 授权：直接用 agent 本地环境里的模型配置，不要另外找 Key

**开跑前不需要向用户索要任何凭据。** 脚本从环境变量读，按顺序取第一个非空值：

| 用途 | 环境变量（按优先级） | 说明 |
|---|---|---|
| 网关地址 | `ANTHROPIC_BASE_URL` | 指向 bmc 中转网关 |
| 鉴权 Key | `ANTHROPIC_API_KEY` → `ANTHROPIC_AUTH_TOKEN` | 通常只有后者 |
| 向量化（可选） | `EMBEDDING_BASE_URL` / `EMBEDDING_API_KEY` | 不设则沿用上面两个 |

**Claude Code 环境通常只导出 `ANTHROPIC_AUTH_TOKEN`，不导出 `ANTHROPIC_API_KEY`。**
脚本已同时认这两个，直接跑即可，不要在每条命令前手动加 `ANTHROPIC_API_KEY=...` 前缀。

同一个网关同时提供 messages 和 embeddings，但**两个端点的鉴权头不同**：messages 用
`x-api-key`，embeddings 用 `Authorization: Bearer`。这是网关背后接了不同后端导致的，
`relay.py` 已分别处理，调用方不用管。

开跑前自检一句（不打印 Key 本身）：

```bash
python3 -c "import os;print('BASE', bool(os.environ.get('ANTHROPIC_BASE_URL')),'KEY', bool(os.environ.get('ANTHROPIC_API_KEY') or os.environ.get('ANTHROPIC_AUTH_TOKEN')))"
```

两个都是 True 就能跑。**不要把 Key 写进脚本、日志、run_manifest 或任何产出文件。**

## 超时与中断：所有阶段都能原地续跑

这条流水线单趟要跑几十分钟，agent 侧的工具超时、网络抖动、进程被杀都会发生。
**处置永远是同一条：重跑那一条命令，不要从头开始，也不要换参数。**

每个阶段都以「文件是否存在」做断点，已完成的批次直接读缓存、不重复调模型也不重复计费：

| 阶段 | 断点位置 | 粒度 |
|---|---|---|
| 00 / 01 / 02 / 07 | `raw/<阶段名>/<batch_id>.json` | 每批 |
| 03（串行） | `raw/entities/<batch_id>.json` | 每批 |
| 04 向量化 | `work/embeddings_cache.json` | 每 20 批落盘一次，异常时也先落盘 |
| 05 / 06 / 08 / 09 | 本地计算，秒级，重跑即可 | — |

实测：微博向量化第一次在第 1280 条超时中断，重跑时缓存命中 70.5%，只补了剩下 536 条。

### 禁止改分块参数，和「失败块要拆小」不矛盾

**重跑时不要改 `--batch-size` / `--cap` / `--top-k`。** 断点是按批次编号对应的，
改了参数编号会错位，已完成的批次对不上、会全部重算，还可能产出编号冲突的事件。

这条和「块太大导致失败要拆小」不冲突，**因为拆小发生在断点粒度以下**：

- **⑦ 的自动二分是在块内部按记录拆的，`block_id` 不变**。60 条的 BLK0000 内部拆成
  30+30 甚至 15+15，写回缓存的仍然是 `raw/block_archive/BLK0000.json`（合并后的产物）。
  实测用当初触发失败的同一组参数原样重跑：调用 0 次、成本 0，直接命中缓存。
- **手动兜底 `x1_presplit_blocks.py` 也不用改 `--cap`**。它直接改写 `blocks.jsonl`，
  只给失败块生成子块编号，成功块的编号原样保留、仍然命中缓存。实测 B站：11 个块里
  7 个走缓存，只重跑了拆出来的 4 个子块。

所以失败块的正确处置**永远是原样重跑**。**唯一真正需要改 `--cap` 的场景**是「想换一套
分块策略整体重跑」——那不是故障恢复，应该新建一个运行目录从 ⑤ 重跑，不要在原目录上改，
否则新旧编号会混在同一份 `raw/` 里。

## ⑦ 的降级链（顺序不能换）

```
① 整块调一次
② 空返回 / 解析失败  → call_json 重试至 5 次，退避 2/4/8/16s（30 秒窗口）
③ 撞 max_tokens      → 原样重试 1 次（输出长度随机，重试常能过，且不切散事件）
④ 仍撞 max_tokens    → 块内对半拆，两半各自递归走 ①~④
⑤ 拆到 12 条以下或 3 层  → 放弃，报失败块，交人工跑 x1
```

**②~④ 全在一次进程内完成**，不需要外部干预，也不需要改任何分块参数。
`--split-floor`（默认 12）和 `--split-depth`（默认 3）只在极端情况下需要调。

**每一级都比下一级更保守，只有上一级救不回来才降级。** 这个顺序是实测定下的：

- ② 在 ③ 之前，因为空返回占实测失败的 3/4，且拆块对它完全无效
- ③ 在 ④ 之前，因为输出长度是随机的，重试免费保住块的完整性，而拆块一定会切散
  跨半区的事件
- ④ 保留而不删掉，因为「块内记录太多、输出真的装不下」是会发生的，那时只能拆

拆过的块会在阶段结尾单独打印一行告警，列出块号与拆分层数——**这些块内部被切开过，
跨半区的同一事件可能出现两次，要复核**。没有这行告警就说明本轮没拆过。

三类 JSON 失败的判别方法见 [pipeline.md](pipeline.md) 的「三类长得一样的 JSON 失败」。

## 并行执行：四平台同阶段并行，不要顺序跑

阶段 03 的串行只在平台内部（Entity 注册表逐批累积），**四个平台之间要并行**——
每个平台有独立注册表，互不依赖：

```bash
S=/mnt/skills/topic6-event-registry/scripts
for p in 微博 抖音 知乎 B站; do
  (cd $p && python3 $S/02_extract_frames.py --run-dir . --batch-size 40 --concurrency 8) &
done
wait
```

墙上时间从「四平台之和」变成「最慢那个平台」，数据语义零变化。实测 3762 条四平台的
阶段 03：顺序跑 25 分钟，改成两两并行 17 分钟。

messages 端点确实能并行——实测 8 个并发请求同时发，单个耗时 38 秒、8 个总共 46 秒，
接近线性。**但 embeddings 端点不是这样**，加并发不涨吞吐，四组对照见 [benchmarks.md](benchmarks.md)。

单阶段耗时超过几分钟就放到后台跑，不要占着前台等 agent 侧超时。

## 成本台账的已知缺陷

**失败运行的花费不会被记进 `run_manifest.json`。** 失败的进程提前退出，来不及写台账，
但那些调用是真的付过钱的。实测 3762 条那次：台账合计 $19.07，而阶段 07 的四个平台里
只有一个把全部调用记进了台账（16 块记 16 次），另外三个分别是 107 块记 4 次、
20 块记 5 次、11 块记 4 次——真实成本约 $24。

要准确核算，得把失败轮次的调用数按每块单价单独估进去。台账本身是 append-only 的，
它防的是覆盖写，防不住进程异常退出。
