# 事件身份判据：Identity Core、State、实体关系

## 一、Identity Core 决定「这是哪件事」

只有这几个字段构成事件身份：

| 字段 | 说明 |
|---|---|
| `actor_id` | 主体（已归一的实体 ID） |
| `action` | 动作 |
| `object` | 动作对象 |
| `event_type` | 事件类型 |
| `anchor` | 锚点（元数据层，跨窗口汇总用） |

**Identity Core 一旦确定，不允许被后续成员扩张。**

判定两条内容是否同一事件，看的是 Identity Core 是否一致，而不是：
- 文本相似度
- 是否共享人物、品牌、题材、城市
- 是否在同一时间窗口
- Embedding 余弦分数

## 二、State 是「这件事现在到哪一步了」

| 字段 | 示例 |
|---|---|
| `latest_value` | 票房 35.4 亿 |
| `latest_stage` | PERFORMANCE |
| `latest_time` | 最新一条成员的时间 |
| `member_count` | 18 |
| `key_facts` | 累积的可溯源事实 |

State 允许随新成员更新。

## 三、Event Drift：这是最需要防的失败模式

允许：

```
票房预测 30 亿  →  票房预测 35.4 亿
（State 更新，Identity Core 不变）
```

禁止：

```
票房预测上调
  → 票房预测 + 救市讨论 + 演员回应 + 行业大盘趋势
（Identity Core 被扩张）
```

第二种的表现形式就是事件名开始需要用「与 / 及」把两件事并列，或者只能叫「某某系列事件」「某某相关动态」。**名称需要并列连词才能覆盖成员，等于承认 Identity Core 已经漂移。**

实测案例：一个 17 条成员的事件被命名为 `胖东来许昌老店关闭房租招聘刑释人员系列事件` —— 名称要靠堆砌才能覆盖成员。在一级 + 二级结构下正确形态是：一级「胖东来本周经营调整」，二级角度「门店关闭 / 房租政策 / 用工政策」。判据是**一级名称能否保持具体**，能就合，不能就拆。

注意「与/及」不能当机械规则用：
- `逝世及各界悼念`、`立案与官方回应`、`登陆及城市影响` —— 同一锚点的**连续阶段**，正确
- `C罗与乔治娜完婚` —— 一个事件的**两个主体**，正确
- `算力融资平台及某公司IPO估值` —— 两家公司两件事，错误

这是语义判断，交模型判，不要写成正则或词表。实测用阶段词白名单+字数阈值实现，判对率只有 28%。

## 三点五、「多个灵感方向」vs「同一方向的多个切入点」

这是全套判据里最容易判错的一处，两个方向都错得很严重。

判断先问一句：**这些热点背后能提供的创作灵感参考，是一个还是多个？**

**多个方向 → 必须拆。** 台风登陆致灾与官方辟谣涉汛谣言，一个是灾情应对、一个是信息治理，硬合并会让事件名退化成空词。

**同一方向的多个切入点 → 必须合。** 一次版本更新、一次电影上映只提供一个方向，它的各个切入点不构成独立事件。

| 场景 | 正确处理 | 主体怎么写 |
|---|---|---|
| 游戏某版本的主线剧情 / 支线 / 新地图 / 卡池 / 新玩法 | **一个事件** | 用游戏名指代 |
| 电影的定档 / 上映 / 票房进展 / 口碑 / 演技讨论 / 细节解读 | **一个事件** | 用片名指代 |
| 同一场典礼的红毯 / 获奖 / 感言 / 票数 / 某明星话题 | **一个事件** | 用活动名指代 |
| 同一主体的多个事项（关店 / 房租 / 招聘政策） | **优先一个事件** | 用主体名指代 |
| 同一组合的不同成员出现在同一场活动 | **归入该活动事件**，各人话题作二级角度 | 用活动名指代 |
| 同游戏的不同版本号、同系列的不同代产品 | 不同事件 | 分别写版本 |
| 赛事的不同届次 / 不同站点 | 不同事件 | 分别写届次 |
| 台风致灾 vs 官方辟谣 | 不同事件 | 分别写 |
| 电影票房 vs 由此引发的行业救市讨论 | 相关事件（REACTION） | 分别写 |

「同一主体的多个事项合成一个」有一条硬约束：**合并后的一级名称必须仍然具体**。如果只能叫「某某系列事件」「某某相关动态」才覆盖得住，说明它们确实是多个方向，必须分开。

实测教训（反面）：不加「同一版本各侧面合并」这条规则时，某游戏一个版本的 7 个侧面（剧情任务 / 支线 / 大世界地图 / 角色卡池 / 某角色设定 / 射击玩法 / 造物机制）被判成 7 个单成员事件，业务侧看到的是 7 条碎片而不是 1 个可用的灵感方向。

实测教训（正面）：一个 17 条成员的事件曾被命名为 `胖东来许昌老店关闭房租招聘刑释人员系列事件` —— 名称需要堆砌才能覆盖成员，就是「一级名称不够具体」这条约束要拦的情况。在一级 + 二级结构下正确形态是：一级「胖东来本周经营调整」，二级角度「门店关闭 / 房租政策 / 用工政策」。

第三方指控 + 当事方回应属于判断项，不是固定规则：争议的讨论体量足以独立支撑一个话题方向时独立成一级，体量小、只是主事件的插曲时作为二级角度。

## 四、Frame 合并规则（防漂移的具体机制）

新成员归入事件时：

| 字段类别 | 合并方式 |
|---|---|
| `actor_id` / `action` / `object` / `event_type` | **只认 canonical 值，不合并**。新成员与之冲突 → 不该归入这个事件 |
| `parent_event_id` | 不变（除非 Parent 归一阶段统一调整） |
| `key_facts` | 累积，同键取最新且保留出处 |
| `latest_*` | 按时间取最新 |
| `member_count` | 递增 |
| `canonical_title` | **不在归入时改**，留到 re-canonicalization 阶段统一生成 |

触发 re-canonicalization 的条件：
- 窗口末统一执行一次
- 归入了一条 `information_score` 显著高于当前 canonical anchor 的成员
- 块内归档把该事件与另一个事件合并了

## 五、实体关系 ≠ 事件关系

这是两套独立结构，互不替代。

### Entity Registry 表达实体谱系

```
ENT001  TFBOYS      GROUP
ENT002  王俊凯       PERSON   parent=ENT001
ENT003  王源         PERSON   parent=ENT001
```

### Relation Graph 表达事件之间的关系

```
EVT_王俊凯品牌活动  --SAME_ENTITY-->  EVT_王源音乐节
```

**关键：同属一个组合只构成 `SAME_ENTITY` 关系，绝不能因此进入 SAME_EVENT。**

传统做法要为此写一条规则（「团体代际冲突必须拆分」），但规则只能表达「不要错并」，无法表达「它们属于同一谱系」。实测某周时代峰峻系艺人散落在 **14 个互不相干的事件**里，靠硬规则拆开后谱系关系完全丢失。

实体谱系 + 事件关系两套结构，不需要为任何具体团体写规则。

## 六、Parent / Sub-event 层级

三层结构：

```
PARENT001  周杰伦2026巡回演唱会
    ├── EVT023  上海演唱会
    │       ├── SUB001  官宣
    │       ├── SUB002  开票
    │       ├── SUB003  正式演出
    │       └── SUB004  演后返图
    ├── EVT031  杭州演唱会
    └── EVT052  成都演唱会
```

模型不需要判断「官宣和演出是不是同一件事」这种两难问题，而是分别判断每条内容的 `parent` 与 `stage`。层级结构由 LLM 明确建立，不是聚类算法「发现」的。

**为什么需要这层结构**：实测某周演唱会类事件 15 个，其中 **73% 是单成员**；作品传播类 105 个，**71% 单成员**；赛事类 57 个，**56% 单成员**。这些碎片既不能合并（不是同一场/同一届），又无法组织（没有上层），是扁平模型的直接后果。

**这三个比例出自一份过采样的测试集**（3 个已知碎片化的簇被 8 倍放大），所以它们只能
说明「碎片这个现象确实存在、量不小」，**不能当作真实分布**——别拿它预估你这一周会有
多少单成员事件。

### Parent 不能由 hint 直接生成

`parent_hint` 是模型给的自由文本，三条记录可能给出 `周杰伦上海演唱会` / `周杰伦2026上海演唱会` / `周杰伦上海站`。

必须走：`parent_hint → Parent 候选召回 → LLM 裁定 → 已有 Parent 或 PROVISIONAL_PARENT`，窗口末再做 Parent Canonicalization。

否则 Parent 数量会和 child 差不多，等于什么都没组织。

## 七、关系类型枚举

`RELATED_EVENT` 必须给出 `relation_type`：

| 类型 | 含义 | 示例 |
|---|---|---|
| `DIFFERENT_PHASE` | 同一事件线的不同阶段 | 演唱会开票 ↔ 正式演出 |
| `FOLLOW_UP` | 后续进展，但已独立成事件 | 事故 ↔ 责任认定结果 |
| `CAUSE_EFFECT` | 一个导致另一个 | 台风登陆 ↔ 某地停运 |
| `REACTION` | 对某事件的回应或衍生讨论 | 电影票房 ↔ 行业救市讨论 |
| `SAME_ENTITY` | 同一主体或同一谱系的不同事项 | 同组合不同成员的活动 |
| `SAME_SERIES` | 同一系列的不同届次或站点 | WTT 瑞典站 ↔ WTT 横滨站 |
| `OTHER_RELATED` | 确有关联但不属以上 | — |

**宁可标 RELATED，也不要为了不丢关系而强行合并。** 强行合并会让事件名无法覆盖成员，是更严重的错误。

## 八、非事件的边界

`NON_EVENT` 的判据是**没有现实触发点**：

- 纯知识科普、教程、攻略、选购建议、健康建议
- 纯观点征集、纯情绪抒发、纯审美展示（穿搭/妆容/风景）、个人日常、游记
- 只有一个宽泛概念或行业名、没有任何具体动作
- 残缺到无法恢复语义

**不可误删**（即使表述口语化）：官方回应、作品上线或定档、产品发布、商业合作、具名营销活动（含平台官方发起的具名话题活动）、赛事进展、公共争议、事件解读。

实测误删典型：`dou来内蒙古`（平台具名营销活动）、`APEC经济体来华热度持续攀升`（具名活动）、`黄晓明刘雨昕合唱空白格`（具体主体+具体动作）、`百花奖造型出图`（具名活动场次）。

判不准时用 `UNCERTAIN`，不要硬判 `NON_EVENT`。只有 `NON_EVENT` 会被真正丢弃。
