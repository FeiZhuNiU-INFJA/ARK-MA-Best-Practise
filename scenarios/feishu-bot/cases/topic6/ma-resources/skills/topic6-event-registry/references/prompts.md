# 提示词

## 提示词的唯一出处是脚本

**不要在这份文档里放提示词全文。** 之前放过，结果是两份规则漂移——文档里还写着
`underlying_event` 的剥壳规则，而脚本里那个字段早就删了。任何看文档改口径的人都会改错地方。

| 提示词 | 出处 |
|---|---|
| ⓿ 清洗核心规则 | `scripts/00_clean_titles.py` 的 `CLEAN_CORE` |
| ⓿ 四套平台规则 | `scripts/00_clean_titles.py` 的 `PLATFORM_RULES`（知乎 / B站 / 微博 / 抖音） |
| ① 事件性判定 | `scripts/01_eventness.py` 的 `SYSTEM` |
| ② Frame 抽取 | `scripts/02_extract_frames.py` 的 `SYSTEM` |
| ③ Entity 归一 | `scripts/03_normalize_entities.py` 的 `SYSTEM` |
| ⑦ 块内归档 | `scripts/07_block_archive.py`，由 6 段拼成（见下） |
| 判定口径（跨阶段共享） | `scripts/eventlib.py` 的 `TRIGGER_RULE` / `IDENTITY_RULES` / `RELATION_ENUM` |
| x2 边界带裁定 | `scripts/x2_confidence_filter.py` 的 `VERDICT_SYSTEM` |
| x3 过拆方向（该合） | `scripts/x3_review_bidirectional.py` 的 `MERGE_SYSTEM` |
| x3 过合方向（该拆） | `scripts/x3_review_bidirectional.py` 的 `SPLIT_SYSTEM` |

看提示词就 `grep -n "SYSTEM\|^[A-Z_]* = " scripts/*.py`，或直接读对应脚本开头。

## 共享判定口径

`eventlib.py` 里三个常量被多个阶段拼接引用：

| 常量 | 内容 |
|---|---|
| `TRIGGER_RULE` | 一级事件的划分判据：这些热点背后能提供的创作灵感参考，是一个还是多个 |
| `IDENTITY_RULES` | 事件身份判据与必须区分的场景 |
| `RELATION_ENUM` | 关系类型枚举与选用约束 |

**改判定口径只改这三个常量。** 在单个阶段里另写一份，两份规则一定会漂移。

## 通用约定

- 只输出单个 JSON 对象，不带 markdown 围栏、不带解释文字
- 所有 `record_id` 原样返回，不得改写
- 每个 `record_id` 恰好出现一次；漏返的由本地兜底，绝不丢数据
- 枚举值一律本地二次校验，非法值落到兜底值而不是报错丢批

## ⑦ 块内归档的提示词是拼出来的

```python
SYSTEM = (角色说明
          + eventlib.TRIGGER_RULE      # 一级怎么划分
          + eventlib.IDENTITY_RULES    # 身份判据与必须区分的场景
          + eventlib.RELATION_ENUM     # 关系枚举
          + SCHEMA                     # 输出结构与硬性约束
          + FEWSHOT)                   # 少样本
```

约 5900 字符，远超提示缓存的 ~1600 汉字门槛，所以块间并发时这一大段只按缓存价计费。
**因此不要为省 token 精简它**——省下的 token 本来就走缓存价，而丢掉的判据会直接变成误合并。

拼接顺序有意为之：`TRIGGER_RULE` 放在 `SCHEMA` 之前，让模型先建立「一级事件 = 一个
创作灵感方向」这个框，再去看输出结构。这一条没有对照实验支撑，改顺序前先做 A/B，
不要当成定论。

## 三处「看着多余、实测必需」的设计

**`event_description` 必填。** 实测去掉它，模型会把两个灵感方向的内容并成一个事件；
要求它写出「谁做了什么导致这件事被讨论」之后，它自己就拆开了——被迫写清触发点时
会发现那是两件事。它同时是人工核对合并对不对的依据，比核对抽象三元组快得多。

**单成员只返 record_id。** 实测让模型给单成员写事件名和描述，产出的是
`《人民の少爷》发布内容引发关注`、`《山海兽医》发布第三集` 这类模板空话。
不参与合并的记录，加工只会浪费输出并诱导编造。

**`name_evidence` 逐项写出处。** 事件名里的每个数字、届次、时间都要能在成员原文里
找到出处。这是本地事实校验的输入，没有它就只能靠人眼抓「第34届」这类凭空推断。

## 少样本必须用真实踩过的坑

`FEWSHOT` 里每个例子都对应一次实跑错误，不是编的：

| 例子 | 对应的实测错误 |
|---|---|
| 票房破 2/5/8 亿 + 预测 35.4 亿 → 一个事件 | 曾被拆成 4 个事件 |
| 台风致灾 vs 官方辟谣 → 两个事件 | 曾被合成「台风白海豚相关」，只能用空词覆盖 |
| 原神 7.0 剧情/地图/卡池/玩法 → 一个事件 | 曾被拆成 15 个 |
| 一场典礼上各明星话题 → 二级角度 | 曾被拆成刘耀文/杨幂/沈腾各自一个一级事件 |
| 锚点用 `电影《欢迎来龙餐馆》` 不用 `沈腾` | 沈腾实测横跨 5 个事件、杨幂横跨 7 个 |
| 锚点不写 `《欢迎来龙餐馆》片方` | 派生后缀让同一锚点裂成两个 |

**加新例子前先确认它对应一次真实错误。** 凭想象加的例子会把模型往没发生过的
方向拽，还会挤占真实判据的注意力。

## Ⓧ 层三个提示词的共同结构

x2 的 `VERDICT_SYSTEM`、x3 的 `MERGE_SYSTEM` / `SPLIT_SYSTEM` 都是「判据 + 分类刻度 +
否决条款 + 关键对照」四段。**关键对照是这三个提示词里最不能删的一段**，因为这一层要判的
恰恰是自动流程判不准的边界情况，正例反例长得几乎一样：

```
属于   易烊千玺一直在抠脑壳     → 他是本届影帝，典礼现场的紧张反应
不属于 易烊千玺还有三部待播作品 → 关于未来作品的话题，不在典礼里
```

同样是「人名 + 动作」，区别只在动作发生在哪。只给抽象规则、不给这组对照，模型会
在两个方向上系统性犯错。

x3 的两个方向的提示词里必须保留三条否决，都对应实跑误合并：

| 否决 | 实测踩过的 |
|---|---|
| 不同届次 / 站点 / 赛季 / 场次的同名赛事绝不合并 | `WTT瑞典大满贯` 与 `WTT横滨冠军赛` 共享锚点、事件名都能写成「张本兄妹同时夺冠」 |
| 泛化锚点下的不相干事项绝不合并 | 锚点是「中国」时下面挂着经济数据 / 生态规划 / 谣言治理 |
| 拿不准就不动 | 错拆能补救（变成独立热点，不丢数据），错合污染整个事件的身份定义 |

**「名称含并列词就该拆」是最容易被写过头的规则。** 实测名称含并列连词的占多成员事件
的 41%，绝大多数是对的（`朱镕基同志逝世及各界悼念`）。所以提示词给的是判据而不是
规则：并列的几段各自有独立主体、而这些主体又不是同一件事的必要参与方，才拆。

## 提示词版本管理

每次改动记进 `run_manifest.json` 的 `prompt_version`，与 `model` 和 `input_hash` 一起绑定。

**换提示词或换模型，置信度校准表作废必须重测**——置信度分布会随两者变化。
详见 [calibration.md](calibration.md)。
