# 热点事件归档

把「标题两两聚类」换成「块内全景归档」：先把可能相关的记录圈成一个块，再让模型一次看完整块、直接给出事件划分。

产物是两层，对着营销洞察的实际用法设计：

```
一级  标准事件名     第38届百花奖闭幕式暨颁奖典礼            ← 这一周发生了什么
二级  宣传角度       红毯及造型 / 获奖结果 / 票数与争议 /     ← 可以从哪些角度做话题
                    落选与回应 / 现场花絮 / 刘耀文相关话题
```

**多成员事件是主要产出**，它们热度更高、能支撑话题和角度。单成员记录不做加工，清洗后的标题直接当事件名。

## 只想赶紧跑起来的话

1. 先确认要的是「本平台这周有哪些事」还是「全网这周有哪些事」——决定跑不跑跨平台层
2. 按「执行」一节的命令依次跑；注释里写了「停下来」的两处必须真的停下来看，它们是
   全流程唯一两个人工门禁，漏了会一路带错到最后
3. `x3` 在单平台路径里也要跑，它补的是「一件事超过 cap 必然落进两个块」——
   分块层修不了，六种改法都试过（见「为什么单平台也要跑 x3」）
4. 跑跨平台的话，接「跨平台合并」一节，五步顺序不能换
5. 中途报错先查 [references/runbook.md](references/runbook.md) 的异常速查表——07 已能
   自动分流恢复，速查表按现象给真因与动作

下面的篇幅大半在讲**为什么每步必须这么做**。这些论证不是背景资料：这套流程的每条规则
都对应一次实跑失败，不知道规则在防什么，改动时就会把防线拆掉。所以遇到「这一步看着
多余」的念头时，回来找对应那一节。

## 作用范围：默认单平台，跨平台是可选层

**默认一个平台一个运行目录。** 平台差异是真的：标题体裁、热度量纲、内容密度都不同,
跨平台判据带来的误合并风险要单独承担。

**但「跨平台增量不值得」这个旧结论已被全量数据推翻**——它依据的 382 条测试集是从
已知碎片化的问题簇里挑的、有 8 倍过采样，比例全都不可信。全量实测：**56.1% 的多成员
事件跨平台**。所以只单平台跑会把同一件事在四个平台上的记录留成四个事件。

要不要合并是业务选择，不是技术结论：

- 只要「本平台这周有哪些事」→ 单平台跑 00~07 + x3 + 08~09
- 要「这周全网有哪些事」→ 加跑 x0~x4

跨平台不做热度聚合。不同平台热度是不同量纲的自造指标，见「热度口径」。

## 两条硬性禁止

1. **不让图算法产出结论。** 不做 Union-Find 判定同一事件，不构建全量连通分量当答案。
2. **不让任何 Embedding 阈值直接决定「是否同一事件」。**

两条都不是审美偏好，是实测撞出来的。最有说服力的一个数字：**同一个阈值参数决定了答案
本身**——0.55 时最大组吞掉全量的 70%，0.65 时只剩 62 个节点。而任何阈值都不可用，
因为精度 64.1% 时召回只有 27.8%。精度这一层只能由 LLM 承担，它对召回提议的候选对
拒绝了 86.6%。

传递性是连通分量的固有属性，不是参数能调掉的。四组对照数据见
[references/benchmarks.md](references/benchmarks.md) 的「阈值路线的失败证据」。

## 但分块可以用传递闭包

这是整套设计的支点，也是上面两条禁止的边界：

- 聚类要**精度**：错一条边就错一次合并
- 分块只要**召回 + 有界**：多塞无关记录只是让模型看到噪声，而模型对噪声的拒绝率实测 86.6%

**图算法不得产出结论，但可以用来划定工作范围。** 在分块里传递性反而是优点——它保证
同主体不被切开。实测 cap60 分块把龙餐馆 55 条、原神 19 条各自完整放进同一个块。

**但用来验证它的 547 对同事件基准不是人工标注**，是上一版路线自己判定的，所以
「召回 100%」既不能证明合并精度，也不能反证这 547 对都该合。局限见
[references/calibration.md](references/calibration.md)。

规模上限按**预估输出 token** 控制，不只按记录数——截断是这套设计唯一会静默污染数据的
失败模式。

## 为什么必须整块一次看完

逐条或逐小批归档会把同主体的记录切散，跨批合并只能依赖「前面批次已经把事件建对」。实测：龙餐馆 55 条被切到 13 个批次 → 产出 10 个事件；原神 19 条切到 3 个批次 → 15 个事件。

`如何评价《欢迎来龙餐馆》这部电影？` 和 `如何评价电影欢迎来龙餐馆` 被分到两个事件——不是模型判错，是它俩从来没被放在一起给模型看过。

整块一次看完同时消掉了顺序依赖：块内没有「第一条记录事实上定义事件框架」的问题，块间不含同事件对，所以不需要临时事件池、事后去重、二轮重跑这些补丁。

### 为什么单平台也要跑 x3

**一件事的记录数超过 cap 时，它必然落在两个块里，而块内看不到彼此。** x3 原先只写在
跨平台层，但这个问题在单平台同样存在——实测《早春晴朗》65 条记录落进 2 个都满了 60 的块，
产出 10 个事件、最大那个只覆盖 63%。

**分块层修不了这件事，六种改法都试过：**

| 改法 | 共块率均值 | 早春晴朗 |
|---|---|---|
| 现状（按 embedding 分数排序，cap 60） | 91% | 65% |
| 排序键换字符 3-gram | 90% | 54% |
| 排序键换分词 + IDF | 75% | 52% |
| 三信号加权 | 92% | 52% |
| 互为 Top-K 剪边 | 85% | 35% |
| cap 提到 80 | 93% | 65% |
| cap 提到 150 | 94% | 71% |

**两条反直觉的结论**：分词+IDF 的两两区分度最高（6.7 倍 vs 向量化 1.1 倍）却分块最差，
因为 IDF 会因稀有词巧合烧掉 cap 名额；剪边更差，因为剪掉了维系整组的传递桥——
分块依赖传递闭包，这是设计支点。提 cap 只是让无关记录进来（cap80 时新进的是
肖战、王一博、易烊千玺），一条该进的也没拉回。

**接 x3 之后早春晴朗 63% → 82%、碎片数 24 → 21 个事件、覆盖 86% → 90%，
微博一周 $0.59。** 前三条召回通道靠锚点字符串匹配，四个早春晴朗事件锚点相同，直接命中。

**第四条通道用的是 06 丢掉的边。** 撞 cap 时被丢的边（微博 10,991 条）落在
`work/skipped_edges.jsonl`，它们正是「召回层认为可能同事件、但装不进同一块」的连接。
锚点匹配配不上的它能配上——`井柏然Luke穿搭走红` 与 `早春晴朗播出` 锚点是两个不相关的
字符串，但之间有 167 条被丢的边。门限 `--cut-edge-min 30`：低了会被并查集传递污染
（≥10 时早春晴朗组里混进刘恋入职奥美、倪妮考科目二），≥30 剩 17 个对、噪声明显少。

**「去掉 cap、超阈值再拆子块」这条路不成立**：去掉 cap 后传递闭包只有 1 个连通分量、
1783 条全在里面，拆它就是分块问题本体。cap 的作用不是限制，是唯一在画边界的东西。

x3 同时做过合方向的拆分，所以它不是只会合——实测微博单平台 737 → 770 个事件
（改名 50、拆出 64、合并把 4 个早春晴朗事件并成 1 个）。

### 运行契约：授权、超时、失败恢复、并行

**开跑前不需要向用户索要凭据**，脚本从环境变量读（`ANTHROPIC_API_KEY` 与
`ANTHROPIC_AUTH_TOKEN` 两个变量名都认，Claude Code 环境通常只有后者）。

**所有阶段都有断点，任何中断后原样重跑即可续跑**，已完成批次读缓存、不重复计费。
这覆盖了绝大多数异常：工具超时、进程被杀、网络断、**API 额度用尽换 Key**、限流。
**重跑时不要改 `--batch-size` / `--cap` / `--top-k`**——断点按批次编号对应，改了会全部重算。
这条和「失败块要拆小」不矛盾：拆分发生在断点粒度以下，⑦ 内部拆记录、`block_id` 不变。

**四个平台的同一阶段要并行起进程**，墙上时间从「四平台之和」变成「最慢那个平台」。
阶段 03 平台内必须串行，但平台间独立——实测顺序跑 25 分钟、并行 17 分钟。

**报错先查 [references/runbook.md](references/runbook.md) 的异常速查表**，它按现象列出
真因与动作。那里还有 ⑦ 的五级降级链、并行写法、成本台账的已知缺陷。最常见的两种误判是
「撞到超时以为要从头重跑」和「为救一个失败块去改分块参数、把已完成批次全部作废」。

## 跨平台合并（可选，x0~x4）

四个平台各自跑完阶段 00~04 之后接上这一层。**x 层不是新流程，是复用 05~07 再加两道复核。**

```bash
# 1. 合库。各平台跑到 04 为止，然后合成一个目录
python3 $S/x0_merge_platforms.py --out-dir merged --from 微博 抖音 B站 知乎
cd merged

python3 $S/06_build_blocks.py --run-dir . --cap 60

# 2. 07 现在会自己重试与拆块，正常跑完就没有失败块。
#    只在它仍报「有 N 个块失败」时才需要这两行（成功的块走缓存不重复计费）
python3 $S/x1_presplit_blocks.py --run-dir .
python3 $S/07_block_archive.py --run-dir . --concurrency 7

# 3. 按归属置信度摘掉搭错车的成员
python3 $S/x2_confidence_filter.py --run-dir . --cut 50 --keep 75
# 边界带交人工填 out/x2_待裁定_边界带.csv 后 --apply-verdict，或 --verdict opus 让强模型判

# 4. 双向复核：该合的合，该拆的拆
python3 $S/x3_review_bidirectional.py --run-dir . --dry-run   # 先看候选
python3 $S/x3_review_bidirectional.py --run-dir .

# 5. 出表：原表原样 + 追加事件归属列
python3 $S/x4_detail_table.py --run-dir . --source <进入阶段00的那份CSV>
```

`--top-k` 从 10 提到 60：**召回只能用 Top-K，不能用阈值。** 实测同事件对的相似度
中位数 0.770，但最低 0.513，任何 ≥0.55 的阈值都会拒掉真的同事件对。

**这一层的存在理由是 07 一次看不全块外的重复。** 跨平台时同一件事的记录落进不同块，
单平台时超过 cap 的事件同样落进两个块——**两种形态都靠 x3 补**，所以 x3 在单平台路径里
也要跑（见「为什么单平台也要跑 x3」）。它的召回通道正好对上：「锚点归一后存在包含关系」
让 `百花奖` 与 `第38届百花奖` 能被放在一起比，「归一后锚点相同」捞回被 cap 切开的大事件。

**x2 与 x3 的顺序不能换。** 先摘掉搭错车的成员再判要不要合并；反过来会把该剔除的记录
一起并进大事件，之后更难摘。x3 内部同理，先合后拆，拆的候选必须在合并落地之后重算。

不出跨平台热度排名。x4 只标「这条属于哪个事件」，排名要另一套口径。

## 平台差异只在清洗这一层

平台的差异在**标题包装**上，不在判定逻辑上。所以阶段 00 按平台走四套清洗规则，
阶段 01 往后全流程共用一套标准——判定提示词只有一份，不会漂。

实测各平台 100 条的包装分布：

| 平台 | 平均长度 | 主要包装 |
|---|---|---|
| 知乎 | 36 字 | **提问外壳 100/100**、书名号 44 |
| B站 | 23 字 | 方括号标签 30、书名号 31、空格分词 13、提问外壳 8、期数 7、emoji 5、竖线 3 |
| 微博 | 9 字 | 空格分词 18，另有大量裸话题词 |
| 抖音 | 11 字 | 基本干净，提问外壳仅 1 |

清洗的唯一硬约束是**只删不加**：不补主体、不补谓语、不补背景，不改写数字形式。
新增数字、新增汉字、**新增顿号**都会被本地校验拦下并回退原标题——错误的清洗把编造
前移到了最早的环节，下游查不出来，比不清洗危险得多。

顿号是后补的一类：它不是汉字、躲过了字符检查，但**加顿号等于断言了一层原文没有的
并列关系**。微博实测这一类误改率 69%（`库克 华为` → `库克、华为`，实际是「库克评价华为」）。

`龙餐馆` 这种裸话题词原样留着，它会在阶段 01 被判成非事件，这是正确结果。

**为什么剥壳不放在判定阶段：** 剥壳是确定性动作，产物（原标题 → clean_title）能逐条
人工验收；判定是语义动作，只能抽样校准。混在一个调用里做，等于把可全量验收的部分
拖进只能抽样的环节，而实测判定这一层最怕负担过重（廉价模型 49% 翻案率就出在这里）。

## 核心判定口径

判定规则集中在 `scripts/eventlib.py` 的 `TRIGGER_RULE` / `IDENTITY_RULES` / `RELATION_ENUM`，被多阶段共享。**改口径只改这三个常量**，不要在单个阶段里另写一份。

### 一级事件 = 一个创作灵感方向

判断怎么划分，先问：**这些热点背后能提供的创作灵感参考，是一个还是多个？**
一个就合成一个一级事件、不同切入点放二级角度；多个就分成多个一级事件。

可核对的代理判据是**触发点**：写不出各自独立的触发点，通常就是一个方向。

不要用「能不能单独成为一条热搜」当判据——票房破 2 亿 / 3 亿 / 4 亿各自都能上榜，但它们提供的灵感只有一个「影片大卖」。

下表是按「灵感方向数」列的**场景类型**，不是题材清单。9 行里有 5 行落在影视游戏，
只因为校准用的样本周恰好如此；财经、科技、体育、社会事件同理套用，不要因为手里的
数据没有影视内容就以为这些规则不适用，也不要反过来专门去找「像百花奖那样」的事件。

| 场景 | 处置 |
|---|---|
| 同一影片票房逐次破亿 + 上调票房预测 | 一个事件，各次进二级角度 |
| 影片上映 + 剧情解读 + 演技讨论 + 隐喻细节 | 一个事件 |
| 游戏某版本的剧情 / 地图 / 卡池 / 新玩法 | 一个事件 |
| 同一场典礼的红毯 / 获奖 / 感言 / 票数 / 某明星话题 | 一个事件，各切面进二级角度 |
| 台风登陆致灾 vs 官方辟谣涉汛谣言 | **两个事件**（灾情 / 信息治理，两个方向） |
| 不同届次 / 版本号 / 赛季 / 场次 | 不同事件 |
| 同一主体的多个事项（关店 / 房租 / 招聘政策） | **优先一个事件**，各事项进二级角度 |
| 同一组合的不同成员各自活动 | 只是实体谱系关系，不同事件 |
| 同一组合的不同成员出现在同一场活动 | 归入那场活动的事件，各人话题作二级角度 |
| 由作品引发的行业性讨论（大盘 / 救市 / 同档期竞争） | 相关事件，不是该作品事件 |

「同一主体的多个事项合成一个」有一条硬约束：合并后的一级名称必须仍然具体。
只能叫「某某系列事件」「某某相关动态」才覆盖得住，说明它们确实是多个方向，必须分开。

**第三方指控 + 当事方回应属于判断项，不是固定规则。** 争议的讨论体量足以独立支撑
一个话题方向时独立成一级；体量小、只是主事件的插曲时作为二级角度。

### event_description 是必填，也是核对依据

一句话说清「谁、做了什么，导致这件事被讨论」。实测去掉这个字段时，模型会把两个方向的内容并成一个事件；要求它写出触发点后自己就拆开了——被迫写清「谁做了什么」时会发现那是两件事。

人工核对合并对不对，看两个事件的描述说的是不是同一个灵感方向，比核对抽象三元组快得多。

### 事件名必须能覆盖成员

这条有**两个相反的失败方向**，只防一头就会滑向另一头：

**太空** —— 禁止「系列事件」「相关动态」「相关内容」「全程追踪」「引发关注」这类空词。
**命中空词 → 先重命名一次，仍不合格才拆成单条。**

这里曾经是直接拆，理由是「名字必须靠空词才能覆盖成员，说明这批成员不该在一起」。
该推理只在空词承重时成立：实测微博一周被拆掉的 28 个事件（140 条记录）绝大多数是装饰性
后缀，`LPL决赛AL夺冠及相关话题` 去掉「及相关话题」就完全具体，25 条记录白毁。重命名一次
后 24/27 合格，`SPLIT_FROM_EMPTY_WORD` 从 93 条降到 10 条、多成员事件 216 → 240。
承重的空词模型第二次也写不出具体名字（`杨洋近期动态引发关注` 剥完只剩人名），
所以拆分的保护作用不变。重命名过的事件标 `RENAMED_FROM_EMPTY_WORD`，
自动进 `human_review.csv` 让人过目。

**太细** —— 拿其中一条的独有细节当整批的名字。实测这是多成员事件命名的主要失败方式：
53 条关于同一部剧的记录（剧集数据、演员花絮、剧情讨论、见面会宣传）被命名成
`栾念为了见尚之桃飞西北20次`。这个名字满足了「不空话」的每一条——具体、有出处、
读得懂、20 字内——但覆盖不了成员。

多成员事件的名字通常是**「主体 + 这批记录共同的动作或状态」**，主体取自锚点，动作取
成员的共同点。上例的正确形态是 `剧集《早春晴朗》播出及口碑讨论`。

本地校验只拦得住「太空」（空词黑名单），**「太细」拦不住**——它在形式上完全合格。
所以这条主要靠 07 的命名规则约束生成，判断方法与示例写在 `07_block_archive.py` 的
`event_name` 一节。

### 单成员记录不加工

只返 record_id，不写事件名、描述、锚点、角度。名称沿用阶段 00 清洗后的 `clean_title`。

理由：不参与合并，加工只会浪费输出并诱导编造。实测让模型给单成员写描述，产出的是 `《人民の少爷》发布内容引发关注`、`《山海兽医》发布第三集` 这类模板空话。

单成员锚点留空，避免 `中国`、`相关政府部门`、`业内人士` 这类泛化主体污染锚点表。

### 锚点是元数据，不是主键

目标是**最小可唯一识别**，不是最通用。判据：换到下一周，同一个名字还能不能指同一个东西。

- 对 → `电影《欢迎来龙餐馆》`、`第38届百花奖`、`原神`、`台风白海豚`
- 错 → `沈腾`（实测他横跨 5 个事件、杨幂横跨 7 个——人物常同时参与多件不相干的事）
- 错 → `电影`、`中国`、`相关政府部门`（没有信息量）
- 错 → `《欢迎来龙餐馆》片方`、`B萌应援参与者`（派生后缀不构成新锚点）
- 例外 → 纯人物话题（`奇文 春雪` 这类创作者内容，没有可指的作品或活动），人物本身就是合格锚点，实测 8/8 正确

## 热度口径

只有一条口径、没有自由参数：平台内百分位，事件热度取成员百分位峰值。公式见
[references/pipeline.md](references/pipeline.md) 的 ⑧。

**不跨平台聚合热度，也不相加原始热度值**——不同平台的热度是不同量纲的自造指标，
即便换成百分位，跨平台相加也只是把「上榜平台多」伪装成「更热」。

热度值解析不了时标成缺失，不当 0。`12.5万` 当成 0 会把当周最热的记录排到最后，
而排序照样出得来、看不出错。阶段 08 会把缺失排除在百分位之外并单独计数。

## Confidence 的处理

两个不同的置信度，规则相反，不要混：

- **模型对自己判定的置信度（`model_confidence`）：只落盘，不做路由。** 不要写
  `>0.8 自动采信` 这类规则，直到跑完一轮 GT 校准——阶段 01 有过实测反例，廉价模型给出的
  「NON_EVENT + 高置信」里 49% 被强模型翻案。**未校准的置信度是没有刻度的仪表。**
- **成员归属置信度（`member_confidence`，07 产出）：可以路由，因为它有刻度。** 刻度写在
  07 的 SCHEMA 里，x2 按 `--cut 50 / --keep 75` 双线处理，不取中间值一刀切——因为分档
  质量两头准、中间浑。

这两个数是在 88 条样本上校准的，不是通用常数，每次跑完要抽查 `out/x2_已剔除.csv`
的头几条。**判不准时先查刻度缺不缺档，别先换模型**——实测换 opus 裁定改对 7 改错 8，
错误全部落在刻度里没写的档位上。

双线阈值的误伤对照表、分档质量分布、校准工具链（`10_build_calibration_sample.py` +
`11_score_calibration.py`）见 [references/calibration.md](references/calibration.md)。

## 跨窗口增量

```bash
# 第二窗口：跑完 01~04 之后插入
python3 $S/00_seed_from_registry.py --run-dir . --prev-registry <上窗口>/out/registry_snapshot.jsonl
python3 $S/05_recall_candidates.py --run-dir . --top-k 10
python3 $S/06_build_blocks.py --run-dir . --cap 60
python3 $S/07_block_archive.py --run-dir . --prior-events work/prior_events.jsonl
```

三条不变量，破了任何一条跨窗口引用就断：

1. **历史 `event_id` 原样保留**，新事件分配 ID 时跳过历史号段。踩过：247 个历史事件被 101 个新事件撞号覆盖，快照显示「新增 0 个」。
2. **历史事件的 Identity Core 不被本窗口成员改写**，只更新 State。
3. **历史锚点先进注册表再归一。** 从空注册表开始会给同一锚点另起 ID——踩过：覆盖率 42% → 6%。

本窗口未触及的历史事件原样保留，`windows_since_update` 递增；超过 `--max-age-windows`（默认 4）不再参与召回，但不删除。

## 向量化用 Doubao-embedding

阶段 04 曾是全流程最慢的一环（1816 条要 20~30 分钟），真因不是网关拥塞、也不是批量或
并发没调好，而是**默认模型选错了**：`text-embedding-3-small` 是 OpenAI 的，要出海。
换成 `Doubao-embedding` 后 1816 条只需 **15.8 秒**，召回质量在两个平台复验持平略优。

**批量和并发调不动吞吐，别在那上面花时间**——四种组合实测全在 0.21~0.26 条/秒，
而同样参数在不同时段差 70 倍。唯一有意义的参数是超时（默认 600 秒，曾是 120 秒，
会把正常的慢请求误杀）。

换模型注意：**维度 2560 与 1536 不通用，已有 embeddings 必须重算**（缓存键含模型名，
不会串档，但旧缓存不命中）。五个模型的完整吞吐与召回对比见
[references/benchmarks.md](references/benchmarks.md)。

## ⑦ 的三类失败已自动分流

⑦ 会区分三种长得一样的 JSON 失败并分别处置：**截断**先原样重试、仍截断才在块内对半拆；
**裸双引号**由 `relay.repair_unescaped_quotes` 自动修；**网关返回空**走长退避重试
（5 次 / 30 秒窗口）而**不拆块**——空返回是并发下的瞬时故障，拆它无效还会切散事件。

正常跑完不需要人工介入。判别方法与实测证据见
[references/pipeline.md](references/pipeline.md)，五级降级链见
[references/runbook.md](references/runbook.md)。

**这类失败压不到零**：实测 121 个块仍会有 1 个空返回撑过 30 秒窗口。但它已经从
「整阶段报错要人工拆块」降级成「原样重跑一次即可」——重跑时已完成的块全部走缓存。

## 验收指标

不用「最大簇不超过 N」这类工程指标——它靠调参就能达成，而调参恰恰是这套架构要消除的东西。

完整指标与抽样量见 [references/calibration.md](references/calibration.md)。三条不能让步的：

| 指标 | 目标 |
|---|---|
| False Merge Rate | 优先压到最低。错拆能补救（记录变回独立热点，不丢数据），错合会污染整个事件的身份定义 |
| 空词事件名 / 名称超 20 阅读单位 | 都是 0。`x3` 出口会打印剩余不合格数 |
| 走 Ⓧ 层时的两条守恒 | 记录总数前后相等、一条记录只属于一个事件。脚本会硬失败，不需要人工核 |
