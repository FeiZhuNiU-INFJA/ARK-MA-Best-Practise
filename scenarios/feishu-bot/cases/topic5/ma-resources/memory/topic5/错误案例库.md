# 错误案例库

> 每次遇到错误并修复后,追加一条记录。格式:`## E{N} · {错误简述}`
> 每次启动前必读,避免重复踩坑。
>
> 新增案例由 gateway 侧 Memory Store API 追加,**Agent 不写**。

---

## 记录规范

```
## E{N} · {错误简述}
- **阶段**:Phase X / 节点 nXX
- **现象**:{什么情况下触发}
- **根因**:{为什么会发生}
- **修正**:{怎么解决的}
- **预防**:{下次怎么避免}
```

## E1 · 依赖文档谎报 skill「已在仓内」,接真时才发现没迁入

- **阶段**:波次 3/4(SSJH / 图表 / 封面 / COS 接真)
- **现象**:`DEPENDENCIES.v0.2.md` 声称 SSJH/图表/封面/COS 四个 B 类 skill「已就绪·已在仓内 skills/」,
  但核查时 `ma-resources/skills/` 实际只有 `pipeline-orchestrator`,其余均未迁入;且路径写成
  `assets/render_from_spec.js`/`assets/cos_uploader.py`,实际在 `scripts/`。
- **根因**:依赖文档的「已在仓内」标注未经核验,与真实目录脱节。
- **修正**:接真前一律 `ls ma-resources/skills/` 核验 skill 真实存在,再核对真实脚本路径;已改依赖文档为
  「已接真(波次N 迁入)」并修正 `scripts/` 路径。
- **预防**:任何「接真」动作前,先核实源 skill 真实存在于仓内,勿轻信依赖文档的「已在仓内」标注。

## E2 · SSJH/DataHub config.json 硬编码真 token,迁入即泄露风险

- **阶段**:波次 3/5(SSJH / DataHub 迁入)
- **现象**:客户 `SSJH-Social-Stat/config.json` 与 `blueai-datahub-skill/.env` 硬编码真实 `api_token`。
- **根因**:客户原始交付把凭据写死在配置文件里。
- **修正**:迁入时**不入库** config.json / .env(`.gitignore` 拦截 `skills/**/config.json`、`skills/**/.env`);
  `skill.py`/`client.py` 改为凭据优先级「入参 > 环境变量 > 本地 config.json」,缺失即 raise;
  生产由 MA Vault 以环境变量注入。
- **预防**:迁入任何客户 skill 前先 grep 真实凭据(`tvly-`/`sk-`/`cli_`/`ou_` 等),去敏后再入库。

## E3 · 候选图连通分量膨胀导致模型输出截断

- **阶段**:语义类节点(观点/聚类)
- **现象**:候选图在不受控时连通分量可膨胀至 1700+ 条记录,单次喂模型导致输出截断或失败。
- **根因**:未对模型处理单元做有界切割。
- **修正**:有界分区(Cap 限制)切割,单块记录上限 + token 预算严格执行,溢出边记录至 `skipped_edges.jsonl`。
- **预防**:批处理类 LLM 调用先估算输入规模,超阈值先分块再喂,不要假设单批能吞下全部。

## E4 · CSV 带 BOM 导致 DataHub 解析首列异常

- **阶段**:波次 5(DataHub 批量标注)
- **现象**:行→CSV 上传 DataHub 时,带 BOM 的 UTF-8 导致首列列名被污染,标注结果回填错位。
- **根因**:默认 `utf-8-sig` 写出带 BOM。
- **修正**:CSV 一律 **utf-8 无 BOM** 写出(规避 SKILL.md 记录的 BOM 陷阱)。
- **预防**:对接外部批处理服务的 CSV,显式用 `encoding="utf-8"`(非 `utf-8-sig`)。
